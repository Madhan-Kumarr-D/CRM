bean scopes:

singletone bean scope - Regardless of how many times a bean with singleton scope is requested, only one instance of that bean is ever created within the Spring application context.

prototype bean scope - The prototype bean scope in Spring creates a new instance of a bean every time it is requested from the container. This means each component that requests a prototype-scoped bean receives a unique object with its own state, unlike the default singleton scope where one shared instance is used throughout the application.

request bean scope - In Spring, a request-scoped bean is an instance of a bean that is created and managed for the duration of a single HTTP request in a web application.

session bean scope - A session-scoped bean in a web application framework like Spring is an object whose lifecycle is tied to a user's HTTP session.

application bean scope - in Spring is specific to web applications and means a single instance of a bean is created and maintained for the entire duration of the web application's ServletContext. This is similar to the singleton scope but tied to the web context.

websocket bean scope - The WebSocket bean scope in Spring creates a new instance of a bean for each individual WebSocket session. This means that every time a new client establishes a WebSocket connection with the server, Spring instantiates a fresh copy of the WebSocket-scoped bean, specifically for that connection.

kafka:

it is a concept used for the resolving the problems between the micoservices tightly compling [ when a service a is calling service b and service b is down for some moment then the service a will not get the response and the rest call would be stuck in a stale mate ]

for resolving this problem a queue struture was made and calls and the communications between the two services will be independent of other services basically all the microservices will be communicating with each other in a independent manner.

the service A will produce an api call [ producer ] and the api call will be received by the service B [ consumer ] this whole kafca works in a producer consumer processes. 

there will be a kafka broker inside that we can have multiple topics and each topic can have multiple partitions inside it

important one partition cannot be shared over the two consumers of the same group [ two consumers can access the same pertition when these consumers were from different group ]

one consumer can access two partitions at same time.

the producer can give the partition key [ as which partition should be assisgned with the produced data ]

there were consumer groups [ few similar consumers wrapped together ]

few kafka brokers were grouped together to form a cluster.

kafka follows leader and follower scheme to tackle fault tolaranace, one partition in kafka broker will be a leader in kafka broker 1, there will be another two partitions in other two kafka brokers that are followers of this leader, the producer will send data to the leader and the data will be syned from the leader to the followers

zookeeper is like a complete manager, it stores the broker, partitiona and the cluster informtations of the kafka and it decides who should be the leader and who should be the follower, and also it decides and controls the leader election of the kafka.
